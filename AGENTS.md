## Working agreement

- Follow the project's actual stack, architecture, conventions, and verification requirements. Do not introduce framework upgrades, libraries, or architecture changes without authorization.
- Before every edit, including a small fix, present a plan with the scope, intended changes, affected files, and verification, then wait for approval. One approval covers the changes and checks listed in that plan. If new effects exceed it, stop the affected work and obtain approval for an updated plan.
- For a clear small change, keep the plan short. For a large change, include tasks and dependencies. Where business or architecture choices remain open, investigate within the assigned scope, present the choices, and let the user decide before proposing edits.
- Select context for the current question or issue. Expand only for relevant dependencies or missing evidence. Distinguish verified facts, inferences, and unknowns; keep findings traceable to sources.
- Create, check, or update project documentation only when a person requests it. Coding does not automatically authorize changes to docs, project profiles, or agent instructions. Report documentation impact for the user to decide.
- For documentation work, establish the configured main/master commit and requested scope; distinguish it from a release if different. Report business/code disagreements. Use EN by default and additional languages only within the authorized scope.
- Verify changes against the approved behavior and acceptance criteria using the project's relevant checks. Report what was actually run, results, and remaining gaps; a command found in configuration is not an executed check.
- End with a concise account of the task result, actual verification and gaps, what can be tried and the expected result, remaining overall work, and the user's next step.
- Commit and push only when explicitly requested.
